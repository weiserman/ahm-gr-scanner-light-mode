Three cooperating leaf modules form a thin data-access layer over SAP Gateway:
- `store.js` owns the single-source-of-truth state via a Vue `reactive` object mounted on `window.__GLOBAL_APP_STORE__`, persisted to `localStorage` under key `vue_sfc_template_store` through a deep `watch`. It exposes `store` (state) and `storeActions` (mutators), with an in-file migration path that upgrades legacy `config.odataUrl` into the current `baseHost` + `poPath`/`grPath` split.
- `odata.js` is the HTTP transport. The active implementation routes every call through a local `/api/net/request` broker endpoint (`executeBrokerRequest`) to bypass browser CORS; it builds Basic-Auth headers, appends `$format=json` (skipping `$metadata` and bound-action namespaces containing `v0001.`), performs a one-shot X-CSRF-Token handshake before mutating requests, and retries once on 403 by refreshing the token. A previous direct `fetch(...)` version is kept as a commented block above line 208.
- `entities.js` defines the `EntityService` facade that composes `store.config` paths with `odataFetch` to implement three business flows: read POs with `_Items` expansion, PATCH individual `GoodsReceipt` lines, and the newer RAP draft pipeline (`POST GoodsReceipt` → POST items under `/_Item` → invoke namespace-bound `Activate` action). It also normalizes raw SAP responses into a flat `{ id, deliveryId, code, targetQty, recptQty, flags, ... }` shape consumed by the UI.

Dependency direction is strictly `entities.js → odata.js → store.js`; `store.js` has no imports from the other two files, keeping the reactive state decoupled from network concerns.
